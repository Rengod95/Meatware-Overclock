# 전달 전 검토와 국소 수정

우선순위는 사실·권한 → 요청/승인 범위 → 관계·전제·사례 → 문서/문단 연결 → 의미 보존 표현이다. 실제 전문 사실은 해당 도메인의 원문과 버전을 확인한다. 연구를 참고했다는 사실이 이 스킬의 효과 검증을 의미하지 않는다.

| 검사 | 근거 | 실패 예 |
|---|---|---|
| scope | 요청·선택된 범위·실제 본문 | 독립 질문에 프로젝트 강제, 작은 질문의 전체 교재화 |
| facts | 본문 위치와 실제 원문·버전, 또는 명시적 가상 모형 | 미실행 성공·출처·설계 의도 발명 |
| learner_evidence | 실제 반응·도움·맥락 | 읽음·칭찬·AI 답을 숙련으로 저장 |
| connections | 필요한 전제·중간 단계·파트 연결 | 용어는 정의했지만 결론이 비약 |
| meaning | 편집 전후 조건·범위·인과·의무 | 쉽게 쓰며 의미를 바꿈 |
| boundaries | 바뀐 조건·대안·가정의 유효 범위 | 사례 하나를 모든 상황으로 확대 |
| artifact_mapping | 실제 원본의 위치와 설명 | 원본이 다른데 설명 강행; 원본 없는 요청에는 비적용 |
| interaction | 승인·읽기/점검·저장 권한 | 무단 확대·퀴즈 강제·자동 저장 |

간단한 채팅 설명은 이 원칙으로 자체 검토하되 별도 파일·표를 강요하지 않는다. 여러 파일은 실제 버전/digest와 근거 위치를 남긴다. 적용하지 않는 항목은 이유를 적고 핵심 실패를 전체 점수로 상쇄하지 않는다. 같은 모델의 재검토는 독립 전문가 검증이 아니다.

필수 사실을 확인하지 못하면 확정 표현을 고치거나 가능한 범위를 제한한다. 부분 검토를 전수 검토로, 자료 품질을 학습자 이해로 표시하지 않는다. 결함이 안 보이면 없던 결함을 꾸미지 않는다.

피드백이 문장 읽기 문제면 표현부터, 단어는 아는데 연결이 없으면 중간 단계부터, 사례는 알지만 판단이 어려우면 최소 대조부터 수정한다. '실제 코드가 다르다'면 원본과 버전부터 확인한다. 같은 사례를 유지해 첫 단절을 보충하고 영향받은 부분만 다시 검토한다. 설명 수정의 성공만으로 원인이나 지식을 확정하지 않는다.
